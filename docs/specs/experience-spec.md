- 状态：待项目方评审
- 版本：0.1
- 日期：2026-09-05
- 产品负责人：项目方（具体负责人待指定）
- 设计负责人：待指定
- 适用范围：桌面优先的 P0 创作工作台，兼顾移动端查看与轻量确认

## 1. 体验原则

- **先给判断，再要决定**：AI 先解释机会与方案差异，不让用户从空白表单开始。
- **创意语言优先**：用户看到 Hook、画面和节奏，不看到模型节点和采样参数。
- **每一步都有产物**：对话沉淀 Project Facts、Proposal、Brief、Storyboard 和 Artifact，不依赖聊天记录作为唯一状态。
- **确认成本与生成成本匹配**：策略确认轻量；高成本生成前必须确认 Storyboard。
- **局部修改**：用户修改一个方向、段落或镜头时，明确显示哪些下游内容会过期。
- **建议可解释但不喧宾夺主**：先展示结论和关键画面，需要时再展开依据与限制。

## 2. 信息架构

```text
项目列表
  -> 新建项目
  -> 创意顾问
  -> Creative Brief
  -> 脚本 / Storyboard
  -> 预览与生成
  -> 成片
```

项目内左侧步骤导航固定显示：`资料`、`策略`、`脚本分镜`、`生成`、`成片`。当前步骤可以回看，修改已确认的上游版本时必须提示影响范围。

内部模型管理使用独立 `/admin` 信息架构，不出现在普通创作者的项目步骤中；详细定义见[模型管理后台体验规格](model-management-console.md)。

## 3. 页面与关键交互

### 3.1 新建项目

主区域只有一个多行输入框和素材上传入口。示例提示围绕任务本身，例如“车型、想表达的重点、必须出现的镜头”，不展示模型说明。

可选的轻量设置：

- 发布平台，默认抖音。
- 账号方向，从 Account Brief 带入。
- 目标时长，默认 20 至 30 秒。
- 真实车型/概念创作切换，默认真实车型。

提交后立即进入 Advisor，输入框保持可继续补充。

### 3.2 Creative Advisor 工作台

桌面端采用三列但不做卡片嵌套：

- 左侧窄栏：AI 对话、用户补充和追问。
- 中央主区：诊断结论与 2 至 3 个方案的并排/分页比较。
- 右侧属性区：已确认 Project Facts、用户素材、Evidence 摘要和待确认冲突。

每个方案首屏只显示：方案名、一句话定位、Hook、关键视觉、预计资源等级和“采用”动作。展开后显示受众、承诺、镜头节奏、结尾、依据、限制和替代方案。

主要动作：

- `采用方案`
- `与另一方案合并`
- `让 AI 调整`
- `坚持我的方向`
- `查看依据`

AI 每轮最多提出一个会阻塞方向选择的问题。可以用合理默认值补齐的内容不追问。

### 3.3 Creative Brief 确认

采用方案后，中间区域切换为可编辑 Brief 摘要：

- 内容类型、受众与本条目标。
- Hook、核心观点和视觉回报。
- 语气、节奏、情绪峰值和 CTA。
- 必须保留与禁止补写内容。
- 可用素材、建议生成方式和资源等级。

用户点击 `确认并生成脚本` 后锁定版本。修改锁定版本使用 `创建修订版`，不覆盖历史。

### 3.4 脚本与 Storyboard 工作台

中央以 `9:16` 预览和时间顺序 Shot 列表为主。每个 Shot 是一个独立可编辑单元，显示固定高度的缩略图区域、时长、画面、旁白/字幕、声音和来源策略。

右侧只编辑当前选中 Shot：

- 镜头目的与画面描述。
- 时长、景别和运镜。
- 车型/人物动作。
- 旁白、字幕和声音。
- 来源策略与替代策略。

工具动作使用图标并提供 Tooltip，例如播放、删除、前移、后移和重新生成。文本按钮只用于明确命令，例如“确认并生成”。

页面顶部持续显示总时长、保存状态、预计耗时和相对资源等级。Storyboard 确认后再提交媒体任务。

### 3.5 生成与成片

生成页按时间线显示每个 Shot 的状态：等待、处理中、可预览、需处理、已完成。失败镜头显示可理解原因和三个动作：重试、使用降级方案、返回修改。

成片页提供播放器、版本、生成摘要和下载。P0 不出现发布、套餐或支付入口。

## 4. Advisor 对话规则

### 4.1 首次响应

AI 不直接输出完整脚本。首次响应顺序为：

1. 用 2 至 4 行复述目标与已识别事实。
2. 指出最重要的内容机会和一个主要风险。
3. 若存在阻塞歧义，只问一个问题；否则直接开始检索与方案生成。

### 4.2 方案比较

三个方案应在叙事机制上不同，例如：

- `产品电影感`：视觉奇观和车型记忆。
- `性能证明`：用场景变化证明通过性。
- `观点/评测`：以明确问题和证据组织内容。

只改变形容词、音乐或颜色不算不同方案。推荐方案必须说明它为什么更符合账号目标、现有素材和日更成本。

### 4.3 依据表达

- `用户事实`：显示为已确认，可由用户修改。
- `公开资料`：可查看来源和访问时间。
- `平台建议`：显示推荐理由。
- `创意假设`：明确为待验证，不包装成事实。

公开案例只用于形成创意参考，不显示“预计爆款”“保证高播放”等确定性表达。

## 5. 状态与版本

| 状态 | 用户可执行动作 | 系统行为 |
| --- | --- | --- |
| `intake` | 补充信息、上传素材 | 提取 Project Facts |
| `researching` | 继续补充、取消检索 | 建立 Evidence Pack |
| `advising` | 比较、追问、修改、合并 | 生成/修订 Proposal |
| `brief-draft` | 编辑、返回策略 | 形成 Brief 草稿 |
| `brief-approved` | 创建修订、生成脚本 | 锁定 BriefVersion |
| `storyboard-draft` | 编辑镜头与脚本 | 更新草稿与预览 |
| `storyboard-approved` | 生成或创建修订 | 锁定 StoryboardVersion |
| `generating` | 查看、取消、局部重试 | 执行 Shot Runs |
| `completed` | 预览、下载、创建新版本 | 保存成片与追溯信息 |

Brief 修订后，旧 Storyboard 不删除，显示“基于旧 Brief”；用户可选择重新生成或保留副本。Storyboard 修订后只让受影响镜头及成片过期。

## 6. 空、加载、失败与降级

- 无账号资料：使用垂直内容包默认受众，并在 Brief 中可编辑。
- 无上传素材：Advisor 说明将依赖公开参考和 AI 生成，不阻塞。
- 搜索无结果：标记“未获得外部依据”，继续提供通用方法方案。
- 车型名称冲突：保留用户确认名称，在右栏显示冲突，不自动改名。
- Advisor 结构化输出失败：自动重试一次；再次失败保留对话并提供重新生成。
- 视频 Provider 失败：优先单 Shot 重试，再降级为图片运动或替代素材。
- 长任务：离开页面后仍保存状态；再次打开从服务端状态恢复。

## 7. 响应式与视觉约束

- 桌面端最小设计宽度 1280px，中央内容优先。
- 768px 至 1279px 时，右侧属性区变为抽屉。
- 小于 768px 时，对话、方案、Brief 和 Storyboard 使用顶部分段 Tab；P0 移动端支持查看、回复和确认，不承诺完整镜头精调。
- `9:16` 画布使用固定纵横比；Shot 缩略图和控制按钮尺寸稳定，加载状态不改变布局。
- 使用中性浅/深背景加少量状态色，避免单一蓝紫色界面。
- 页面不使用营销式 Hero，不用装饰性渐变球或大面积说明卡片。

## 8. 可访问性与操作质量

- 所有图标按钮有可访问名称和 Tooltip。
- 键盘可完成方案选择、对话输入、镜头切换和确认。
- 状态不能只靠颜色表达。
- 对话与生成状态使用 `aria-live`，但逐帧进度不频繁打断读屏。
- 删除、取消运行和使下游版本失效的操作需要明确确认。

## 9. P0 验收场景

### 场景 A：张雪 800X

用户只输入已有文字。系统识别车辆事实和必需镜头，给出至少两个方向。用户采用电影感方向并保留 360 环绕和高速骑行高潮，完成 Brief 与 Storyboard 两次确认。

### 场景 B：春风 800MT

系统把沙漠行驶和仪表特写拆成原子镜头，保持用户指定顺序，提出“性能证明”和“产品电影感”等不同方向。用户能合并方向，并在不重做其他镜头的情况下修改涉水镜头。

### 场景 C：跨垂直验证

输入一条育儿选题时，系统不显示车型或 Blender 字段，改用受众问题、知识步骤、演示和收藏价值等建议，证明 Advisor Playbook 来自内容包。

## 10. 待评审项

1. 是否接受 `资料 -> 策略 -> 脚本分镜 -> 生成 -> 成片` 的步骤结构。
2. 是否接受 Creative Brief 与 Storyboard 两个确认点。
3. Advisor 是否使用左对话、中方案、右事实/依据的桌面布局。
4. P0 移动端是否只需查看、回复和确认，不承担完整镜头精调。
5. 用户是否需要在 Proposal 阶段看相对资源等级，还是只在 Brief/Storyboard 阶段显示。

## 11. 通过条件

- 产品方确认信息架构和两个确认点。
- 三个验收场景都有可点击线框或实现后的端到端路径。
- 所有状态、空状态和失败状态在实现前都有对应测试用例。
- UI 不暴露外部工作流产品的节点概念或底层模型参数。
