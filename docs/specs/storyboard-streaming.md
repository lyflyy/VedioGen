# 脚本生成流式接收

日期：2026-09-13。状态：已实现，原项目真实生成验证通过。

## 问题与修复边界

GPT-5.5 的完整分镜输出超过原配置的 120 秒等待上限。单纯改为 300 秒后，非流式请求又遭遇中转站 Cloudflare HTTP 524，因此需要同时调整等待配置和响应接收方式。

仅脚本生成调用 `complete_json(stream=True)`，使用 Chat Completions 的 `stream` 和 `stream_options.include_usage`。其他短请求保持原模式；模型 ID、Key、Base URL 与路由均不更换。当前真实 GPT 部署超时通过现有管理接口从 120 调至 300 秒，并重新探测就绪；其他模型默认值没有批量变更。

## 接收与保存契约

- 使用 `httpx-sse` 0.4.3 解析 SSE 帧、心跳和分隔，不自建 SSE 协议解析器。
- 聚合首个 choice 的 `delta.content`，保留实际 model、请求 ID、最终 usage；忽略 reasoning_content 等内部思考字段。
- 必须收到正常 finish_reason=stop 及终止标记，才能继续 JSON 解析和原有业务 Schema 校验。断流、长度截断、错误帧不能生成部分脚本文档。
- 上游忽略 stream 并返回普通 JSON 时兼容原有完整响应解析，不自动重复发送请求。
- 输出内容限制 100 万字符。按收到数据块检查流式总预算，心跳也检查；网络静默则由读超时终止。该检查不是独立硬截止定时器，静默读的等待仍受 read timeout 控制。
- 连接/连接池等待最多 20 秒，写请求最多 60 秒，并均不超过模型配置值；响应读等待采用模型配置值。
- 超时记录具体阶段（Connect / Read / Write / Pool）、等待上限、实际耗时和脱敏接口地址。
- 流内 rate_limit_error 沿用凭据冷却，不在同次请求中隐式重试。

脚本结果仍由原有持久任务执行器生成、校验、匹配并保存。流式传输用于避免长时间等待整份响应的网关问题，不承诺消除供应商所有 524、限流或故障；本轮没有向页面直播 JSON 或模型内部推理。
