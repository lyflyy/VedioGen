# 企业内部 MVP：样片优先计划

- 状态：内部应用定位与治理后置为用户已确认方向；本文具体范围、评分和排期为待检阅建议。
- 日期：2026-09-06
- 当前优先级：先通过平台做出人工认可的 80 分视频，再逐步补齐长期工程能力。
- 生效范围：取代此前“先完成 A/B 整改与 R0 发布门，再进入真实视频”的近期执行顺序。旧评审的问题仍然成立，但不再全部作为内部 MVP 的前置条件。
- 本轮只调整规划，没有切换模型、调用付费服务或开始应用开发。

## 1. 重新定义 MVP

面向企业内部内容人员，先服务一个共享工作区和少量可信操作人员。项目是可反复使用的平台和工具，不是由开发人员手工在平台之外剪出一条样片后宣告完成。

第一目标：用户输入想法或上传照片，通过 GPT 讨论内容并整理脚本，确认后生成真实镜头，选择/重做局部镜头，最终在页面下载带字幕和声音的竖屏视频。

先做一个推荐方案，允许对话修改，不强制每次三套策略。保留“选方向”和“确认脚本开始生成”的轻交互，不建设正式审批、内容版本树或团队签核。

本次不建设法律风险、违规内容或品牌审批系统。仍需要检查文件能否读取、脚本能否解析、镜头时长是否可执行；这些是生成参数检查，不是内容治理。上游模型自己的限制无法由本平台关闭，失败时如实提示并允许人工处理。

## 2. 必做、简化、后置

| 项目 | MVP 决定 | 长期处理 |
| --- | --- | --- |
| 输入与 GPT 咨询 | 文字、照片；给建议、问必要问题、可修改脚本 | 完整证据链、账号记忆、复杂检索与视频分析后续扩展 |
| 真实视频生成 | 接一个实际可用的视频 Provider，先验证高风险镜头 | 多供应商自动路由、熔断和复杂降级后置 |
| 管理配置 | 沿用现有 Admin，补视频地址、Key、模型、提交/查询和真实结果 | 完整能力矩阵、影子测试、灰度发布后置；未做的检查不显示通过 |
| 内容确认 | 页面明确展示即将生成的脚本，用户点击开始 | Approval 表、版本哈希、不可变文档、冲突合并与历史回滚后置 |
| 任务执行 | 单机低并发、后台执行、保存任务 ID/输出、页面刷新可查 | 完整 Outbox、分布式队列、自动崩溃恢复和补偿后置 |
| 编辑与重试 | 当前草稿覆盖保存；生成中先锁定该项目编辑；手动重做单镜头 | 多人同时编辑和细粒度版本协作后置 |
| 质量检查 | 人工看样片，机器只检查可播放、时长/尺寸、缺镜头等 | 模型视觉评分、全自动语义质检平台后置 |
| 权限与工作区 | 内网/VPN 或现有统一入口访问，先一个共享空间 | 自建账号体系、RBAC、多租户、完整审计后置 |
| 费用 | 开始试验前人工设限，有限重试，保存用量/费用状态 | 多级预算账本、额度结算和复杂成本分摊后置 |
| Blender | 有现成准确资产且环绕必须保真时才接固定模板 | 从零影视级车辆建模、任意资产自动化和渲染农场后置 |
| 测试 | 关键 API/Adapter Mock + 浏览器主流程 + 真实样片 | 大规模故障注入、并发矩阵和 120 次模型评测计划后置 |

不把内网等同于不需要保护 Key：密钥仍只在服务端保存，不回显，不提交到 Git。没有现成访问入口时仅绑定本机/受控网络，不把无保护 Admin 公开上网。这不要求先开发整套权限系统。

## 3. 80 分怎么判断

80 分是项目方对成片可用性的评价，不是模型自动打分，也不等于所有车型都达到影视级。建议按下表人工评分，开始前共同选定参考样片/截图和可接受缺陷。

每项打 0 至 5 分：0 为未实现或不可用，3 为可用但问题明显，4 为少量瑕疵、不影响使用，5 为达到约定参考水平；1、2 为严重程度介于 0 与 3 之间。总分为各项 `权重 × 得分 / 5` 之和。

| 维度 | 权重 | 重点 |
| --- | ---: | --- |
| 脚本与诉求 | 20 | 有吸引力且有节奏，必需镜头、顺序和结尾得到体现 |
| 主体一致性 | 25 | 指定车型轮廓、颜色和显著部件一致，骑手外观不明显跳变 |
| 画面质感 | 20 | 清晰、构图合理、灯光协调，无明显生成伪影 |
| 运动与衔接 | 20 | 运镜自然、驾驶动作可信、转场和节奏流畅 |
| 声音与字幕 | 15 | 音乐/环境音协调，字幕正确且可读，不遮关键部件，无明显爆音 |

建议通过条件：总分至少 80，主体一致性与运动各至少 4 分，其余各至少 3 分，项目方明确接受。参考片和分数由人工定，不承诺播放效果。

以下问题不能靠其他维度高分抵消：错车型、车轮/车架或骑手明显变形穿插、遗漏用户指定的关键镜头、无法播放、缺失计划中必需的画面/音轨、把测试预览或静态缩放冒充真实驾驶。轻微背景瑕疵可接受，不要求像素级复现和毫米级结构测量。

建议第一条 15 至 25 秒、9:16、最终 1080 × 1920 MP4；具体时长依供应商可用镜头时长再确认。转码放大不等于增加细节，不能用输出尺寸冒充画质提升。旁白先可选，音乐/环境音和字幕优先。

## 4. 近期执行顺序

### 第一步：确定画面基准和单一生成路径

- 使用“张雪 800X”作为第一条样片，保留车辆细节、环绕、最后皮衣骑手驾驶的要求；车型身份及参考资产由项目方确认，不能自动替换为相似车型。
- 检查现有中转站可用的图片/视频接口资料及权限，不能仅根据模型列表名称判断可用；没有视频接口就另接一家 Provider，不更换现有 GPT 作为前置条件。
- 准备一组真实车型参考图、一至两个目标视频参考，以及本轮试验费用和等待上限。凭据仍在 Admin 中配置。
- 真实 360 度与单图视觉环绕需明确选择：可接受视觉环绕就先走参考图生视频；必须真实完整 360 度则需要环车素材/多角度参考及经过验证的方案，或可用 3D 资产。

退出结果：确定一个 Provider、输入方式、画面基准、试验额度和环绕要求。未具备新视频凭据前可以做 Adapter Mock 和页面接线，不能宣布真实生成已经可用。

### 第二步：先验证两个难镜头，不先补齐治理系统

- 从平台的薄适配器/内部测试入口提交车辆环绕与皮衣骑手驾驶两个镜头，优先揭示车型变形和动作失败风险。
- 保存真实供应商任务 ID、素材引用、结果文件、耗时及实际/未知费用状态。先每镜头一个候选；需要重试先看结果和剩余额度，不批量盲试。
- 项目方按主体、画质和运动评审镜头。若关键动作不可用，优先调整参考素材、运镜难度或 Provider；改变用户要求必须重新说明并获得接受。
- 达到限额仍不合格就停止，报告具体差距。不能用三维标题、转码或模型高分来掩盖画面不足。

退出结果：可用关键镜头及实测参数。这个 POC 只证明路线可行，不代表平台 MVP 已完成。

### 第三步：接通第一条完整平台流程

```text
输入想法 / 上传图片
  -> GPT 推荐方向并讨论
  -> 可编辑脚本和镜头列表
  -> 用户确认，开始生成
  -> 逐镜头生成 / 查看结果 / 手动重做
  -> 字幕 + 音乐或环境音 + FFmpeg 合成
  -> 在线预览 / 下载
```

- 复用现有页面，不先重做设计系统；生成页显示等待/执行/失败/完成与真实预览。
- 将已验证镜头方法用于该片其余细节镜头；稳定主体参考跨镜头复用，不逐镜头任意改变车型。
- 文本通常是主要输入，因此提供轻量车型参考素材池：文字命中已整理车型时，展示参考图供用户确认；未命中时由内部人员补充/选择素材，或接入经验证的生图能力后生成参考图再确认。不能用通用摩托车图默默替代真实车型。
- 第一版允许人工挑片、补素材、改 Prompt 和选择镜头；最终提交、结果保存与合成下载必须走平台。人工介入次数记录下来供后续自动化排序。
- 生成时只保存本次实际发送的脚本和参数作为任务数据，不建设内容版本控制系统。正在生成的项目先禁用编辑；完成后编辑当前草稿，已有文件不覆盖。

退出结果：第一条片从浏览器输入开始到下载，人工评分达到约定的 80 分；同时确认页面不会返回固定 Fake 成片。

### 第四步：验证不是一次性样片

- 第一条通过后，再做“春风 800MT”：保留先环绕、沙漠与仪表特写、涉水抬头、山林无人机远拉的顺序；复杂场景可逐镜头人工选片，但不得静默删掉难镜头。
- 至少一条从照片输入、一条从纯文字加已确认参考素材开始，验证两种入口，不要求任意未知车型都能自动生成。
- 在新项目中重复跑通主流程；演示失败镜头单独重做、刷新后找回任务，以及下载真实输出。
- 验证成片人工至少 80 分，记录成本、等待和手动处理过程。第二例不过关时按实际支持范围报告，不宣称整个越野镜头能力已完成。

## 5. 最小技术方案

保留 Next.js + FastAPI、现有 SQLite/本地文件和 GPT Adapter，不为内部 MVP 强制迁移 PostgreSQL、部署 Redis 或选择完整工作流引擎。

- 增加一个视频 Provider Adapter，暴露提交、查询、下载；取消仅在 Provider 支持时提供真实取消，否则只停止本地等待并说明可能继续计费。
- 单机后台执行采用受限执行器与现有数据表扩展：先限制一个生成项目同时运行、逐镜头顺序提交；进程内启动不等于持久队列。API 尽快返回任务 ID，页面轮询。
- 保存项目、任务状态、供应商任务 ID、请求参数、片段和最终文件。服务重启后允许操作人员按已保存 ID 查询/接回结果；提交结果未知时标为待人工核对，不自动重发。不承诺无人值守恢复。
- 最小防重复：页面生成按钮禁用，服务端用数据库中的活动任务判断/条件写入阻止同项目重复提交。它不是完整跨系统 exactly-once 保证。
- 本地文件即可保存结果；云模型输入优先使用它支持的直接上传。若必须公网 URL，再增加一个对象存储适配器，不先铺全部存储服务。
- FFmpeg 消费实际片段；手动选择满意片段后合成，保留原片段便于重做。不用固定 6 秒测试片作为最终输出。

代码只检查执行必需的结构、时长、文件和参数，生成前一次确认当前内容。已发现的复杂版本一致性问题留作后续工作，不在本阶段实现文档哈希、版本树和审批聚合。

## 6. 最小验收与费用边界

测试规模随 MVP 缩减，但“真实调用、真实片段、真实成片”不能缩减：

1. Adapter Mock：成功、认证失败、任务失败、查询/下载超时，不消耗真实费用。
2. 浏览器 E2E：输入/上传 -> GPT 整理或隔离 Fixture -> 编辑确认 -> 生成状态 -> 局部重试 -> 下载；测试环境不复用内部真实路由。
3. 预算受控真实验收：按上述两条样片实际执行，并保留 GPT/视频请求标识及文件；与 Mock 结果分开报告。
4. 最小媒体检查：文件可解码、尺寸/时长符合已确认计划、镜头齐全、计划音轨存在；画面与节奏由人工验收。

不等待完整 Schema 集迁移、所有错误分支、压力测试或自动视觉评分平台。仍不能把“未测试”写成“通过”。

生成成本先记实际可得用量、调用次数和供应商账单；价格未知明确显示未知。真实试验设人工确认额度与供应商可用限额，不建设全套额度账本。秘钥保护和不误触发真实付费测试保留。

## 7. 长期目标重新排序

下列窗口用于安排投入，不是延期做样片的理由，也不是质量保证。视频权限、参考资产和预算具备后先推进前两轮，按实际耗时重估。

| 阶段 | 目标窗口 | 聚焦内容 | 进入下一阶段的依据 |
| --- | --- | --- | --- |
| 内部 MVP | 接下来 2 至 4 个开发迭代，优先首轮关键镜头 | 两条 80 分样片、输入到下载、简单配置、人工选片和重做 | 真实质量、可重复流程和试验成本获项目方接受；迭代不预设为固定周数 |
| 内部稳定工具 | MVP 后约 1 至 3 个月 | 日更使用、模板/素材复用、减少手动操作、按真实故障补恢复 | 内部人员愿意持续使用，合格成片成本和等待可接受 |
| 质量与领域扩展 | 约 3 至 6 个月滚动评估 | 车型资产/Blender 精品模板、语音与声音、一个母婴或育儿内容形态 | 摩托车稳定；第二领域有明确输入、镜头和独立人工质量基线 |
| 按需企业治理 | 约 6 至 12 个月或需求提前出现时 | 多人冲突、内容历史、权限、审计、自动恢复、模型发布与性能扩容 | 由实际协作规模和故障成本触发，不按日历机械堆功能 |

模型升级也从小样开始：先比较两个现有样例的修改次数、关键画面约束和成本；当前 GPT 达标就保留。只有创作质量或效率确有收益才换对应任务模型，不先建完整评测/灰度系统。

### 后置能力什么时候重新启动

- 多人频繁覆盖草稿、确需找回历史时：内容版本、冲突控制、审批记录。
- 重启和人工核对已明显拖慢日更时：持久队列、恢复、幂等和对账深化。
- 不同内部团队需要隔离或敏感资料扩大时：细分角色、工作区、审计和保留策略。
- Provider 费用或失败成为主要问题时：价格配置、自动备用路由、较完整的模型评测。
- 稳定实拍/生成无法满足产品环绕特写时：投资准确 3D 资产和固定 Blender 模板。
- 出现外部用户计划时：重新评估之前后置的开放服务要求，不直接暴露内部 MVP。

## 8. 下一轮开发的明确范围

下一轮应做“接入一个视频 Provider + 两个关键镜头 POC + 页面可查看真实结果”，不再以完成旧 A/B 全套整改为前提。

当前仅有 GPT 中转接入的历史证据，没有已验证视频接口。开始真实生成仍需要：

- 一个可调用的视频模型服务及权限；先核实中转站是否已有，没有则由项目方选择/开通一家。
- 本轮最高试验支出和可接受等待时间。
- 首个真实车型参考素材，并确定环绕是视觉效果还是必须精确完整 360 度。

等待这些信息时可实现最小视频接口、模拟任务、页面状态和合成接线，不假装已经调出视频。凭据通过管理后台录入，无需再次贴到聊天或文档。
