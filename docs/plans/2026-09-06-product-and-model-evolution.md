- 状态：待确认
- 日期：2026-09-06
- 本轮诉求：明确如何规划、升级和迭代，以及新模型如何为项目产生实际价值。
- 依据：[架构复核](../architecture/2026-09-06-architecture-review.md)、[工程整改计划](2026-09-06-architecture-hardening.md)、[模型接入规格](../specs/model-provider-routing.md)。

## 1. 总体选择

以“用户输入想法，平台帮助决策，确认后产出可信视频”为主线，不以接入多少模型、增加多少页面作为进度指标。

保留现有技术栈和 Creator/Admin 两套工作区，推进三条相互配合的工作线：

| 工作线 | 要解决的问题 | 成果 |
| --- | --- | --- |
| 产品 | 用户是否获得合理建议，能否理解取舍并确认内容 | 创意顾问、可编辑蓝图、逐镜头反馈、真实下载 |
| 平台 | 确认是否有效，任务是否可靠，费用与来源是否可追溯 | 版本/审批、持久任务、Provider 能力、费用和产物账本 |
| 模型 | 哪个部署在什么任务上更值得使用 | 固定评测集、分能力路由、模型发布与回滚 |

三条线可以交错推进，但真实执行必须遵守工程门。可以先离线评估模型的创意质量，不必等待所有 Worker 完工；不能提前开放不具备确认和预算保护的付费生成。

### 两种“新模型”必须分开

1. 编码助手：用于理解代码、制定方案、实现和验证。其模型或工具升级不会自动成为线上产品能力。
2. 产品运行模型：用户通过平台实际调用的 Deployment。历史已验证部署是 `gpt-5.4-mini`，本轮未重新探测；候选升级模型 ID 尚未选定。

因此，不直接把平台所有调用切到编码助手同名模型，也不假设自有中转站提供该模型。先确认可访问的准确模型 ID、协议、能力和价格，再按任务选择。

## 2. 新模型可以在哪些地方产生价值

下面是需要验证的收益方向，不是对未知候选模型的性能承诺。

| 产品能力 | 如何利用模型 | 用户实际获得什么 | 程序与验收边界 |
| --- | --- | --- | --- |
| 创意咨询 | 结合账号、受众、日更目标和素材，发现缺失信息，给出有取舍的方向 | 不只“照着生成”，而是知道为何推荐某种拍法 | 硬约束与建议分开；不能保证播放量或转化 |
| 素材理解 | 对选定图片或视频抽帧做观察，建立 Asset ID 对应的描述和疑点 | 知道素材够不够、还缺什么、哪些镜头做不了 | 用户声称、视觉观察、外部证据分开；单图不推定车型背面结构 |
| 检索辅助 | 生成检索问题、比较来源、提出冲突澄清 | 文案和参数有可查看的出处，不靠猜测 | 搜索由工具真实执行，保存来源和时间；没有结果就明确未知 |
| 分镜导演 | 将已确认 Brief 转为镜头顺序、画面、动作、运镜、声音和节奏 | 更少遗漏，更容易局部修改 | Schema、时长、首尾约束、引用和可执行策略由代码校验 |
| 自然语言修改 | 把“第二镜头更有力量”等反馈变成明确修改提案 | 看见改哪些镜头、是否重生成、增加多少消耗 | 先展示差异；影响已确认内容时创建新版本并重新确认 |
| 视觉复核 | 对参考图和输出采样帧比较主体、颜色、部件和画面内容 | 辅助发现车型漂移、缺失内容和明显瑕疵 | 抽帧不能证明全片时序正确；机器媒体检查及人工验收仍保留 |
| 日更规划 | 利用用户明确保存的账号偏好和已发布内容记录提出下一条选题 | 减少重复选题，形成系列内容 | 首期使用显式记录，不无限拼接聊天；发布数据没有接入就不声称知道表现 |

不需要为表格每行都创建独立 Agent 或额外模型调用。先用阶段化服务和类型化工具实现；只有流程分支复杂度已被验证，才评估 LangGraph 等编排库。

### 第一个样例的目标体验

用户输入“张雪 800X，360 环绕、细节、最后皮衣骑手高速驾驶”，平台应当：

1. 提取车型名称和三个硬要求，不静默替换为其他车型；身份或素材不确定时请求补充/确认。
2. 区分“真实车型 360 度资产镜头”和“单图生成的环绕感”；说明当前可执行路径和缺失素材。
3. 给出少量适合该账号的方向，例如机械细节展示、人物驾驶叙事，并说明差异、素材需求和资源等级。
4. 用户确认 Brief 后生成分镜，最后镜头保留驾驶内容；CTA 可叠加在镜头中，但不能擅自另加结尾镜头。
5. 用户再确认分镜和资源预算，系统生成；修改某个镜头时明确复用范围和额外费用。
6. 交付有真实来源的片段与合成结果。模型建议、实际工具执行和用户确认在界面上可区分。

## 3. 按产品结果划分发布批次

下面的 R0 至 R4 是本路线图中的批次代号，不修改应用版本号。详细工程任务继续使用原整改计划 A 至 E，不再维护第二套任务清单。

| 批次 | 用户可验收的结果 | 主要范围 | 依赖与退出条件 |
| --- | --- | --- | --- |
| R0 可信创作底座 | 当前 GPT 流程可完成、刷新恢复，不重复建任务，不绕过确认 | A + B；测试隔离、契约、审批、权限、幂等、Worker、真实后台检测 | 无需新视频 Key；失败/重启/并发回归与浏览器流程通过 |
| R1 创意顾问升级 | 用户输入思路，收到可解释建议，能讨论修订并确认脚本蓝图 | C；Facts/Constraints、账号上下文、素材观察、候选模型小样评测 | R0 提供运行保障；用户两个样例硬约束通过，界面展示依据和缺口 |
| R2 真实单镜头 | 参考图或素材确实进入执行，返回一个可追踪的真实镜头 | D；单一视频 Adapter、存储、Manifest、费用、下载 | 用户选定视频 Provider 和试验额度；真实镜头质量、恢复和成本验收 |
| R3 真实多镜头成片 | 两个摩托车样例从输入到下载完整跑通，可局部重试 | E；逐镜头生成、音轨/字幕、FFmpeg、QC；有资产时接 Blender 分支 | R2 通过；机器媒体检查 + 用户人工样片验收，不用固定预览替代 |
| R4 日更与领域扩展 | 小规模真实创作者重复使用，并可切换第二内容方向 | 日更选题、历史复用、失败运营、内容包；先育儿演示，再独立领域验收 | 摩托车闭环稳定；核心状态机不因内容包改变，领域质量规则单独验证 |

首个真实价值里程碑是 R2，不必等所有 3D 资产、完整时间线编辑器或第二领域都完成。R3 中生成视频、用户视频、Blender 各自验收，不能把一个分支成功泛化为其他分支可用。

### 迭代节奏

- 每个小切片只解决一个完整行为，例如“Advisor 请求超时后刷新可恢复”，包含 API、必要 UI、失败测试和证据。
- 建议每周安排一次可运行演示及文档检阅；每周可能完成多个切片，也可能只完成一个复杂切片，不承诺一个发布批次必然一周完成。
- 一个切片通过后再扩大影响面，避免同时改模型、Prompt、Schema、队列和所有页面，导致失败无法归因。
- 周期结束记录完成项、未通过项、实际调用成本和下一切片；不以“页面已经写完”作为里程碑完成。
- 当前没有人员配置、稳定视频供应商和渲染耗时基线，暂不做精确日历承诺。R0 第一条持久任务和 R2 首个真实镜头测量后再调整排期。

## 4. 模型升级方法

### 4.1 按任务而不是按品牌分配

沿用 `fact-extractor`、`creative-advisor`、`storyboard-generator`、`visual-reviewer` 等能力别名。

- 结构简单的事实抽取、分类与字段归一：选择达标后更快、更经济的部署。
- 创意取舍、复杂分镜和多轮修改：比较高质量候选与当前基线，质量收益明显才升级。
- 图片理解与视觉复核：必须实测图片输入；视频先按抽帧路径评估，原生视频支持另测。
- Brief 字段合并、总时长、版本哈希、任务状态：优先确定性程序，不因模型更强而多调用一次。
- 媒体生成：仍使用真实视频/图片服务或 Blender；文本模型不能代替这些执行引擎。

同一模型可以承担多个别名，不需要一开始买多家服务。常规任务不默认走最贵部署；多次重试、复核和影子测试都计入额度。

### 4.2 后台升级操作

管理员完成以下界面流程，不通过修改业务文件换模型：

1. 新增候选 Deployment，绑定已有或新 Credential；导入模型列表只能证明名称存在。
2. 单独测试认证、文本/中文、结构化输出、图片、工具调用、流式和必要上下文。每项显示未测试、通过、失败及真实证据。
3. 选择固定项目快照，对比现有与候选模型的结果、差异、耗时、Token 和费用状态。
4. 建立路由草稿，仅替换受益能力；Prompt、Schema、工具和参数都独立版本化。
5. 在管理员测试账号上受控试用，再按稳定账号分组灰度，保存分组和路由版本；同一个 Run 中途不切换。
6. 达标后发布。不达标时回滚新请求；历史 Run 保留原快照，重新执行必须创建新 Run。

现有 Playground 不能直接承担这项职责，必须先完成 A4 的真实验证整改。供应商别名可能在后台改变模型行为，应记录可获得的供应商模型标识并定期重测，不能声称外部模型权重永远可重现。

### 4.3 兼容性不能靠“OpenAI-compatible”推断

当前已验证路径是 Chat Completions 风格适配器。新模型若需要其他端点、不同参数或工具事件协议，应在 Adapter 内增量支持，不能仅改模型名后上线。

不支持的推理参数、流式、内置搜索或工具协议不展示为可配置能力。模型工具调用只是建议执行请求，实际工具必须经过平台权限、参数、预算和审批校验。

工具返回的网页和素材描述作为不可信数据，不得覆盖系统约束、访问任意内网地址或触发未确认的生成。长上下文也不等于无限记忆：按账号归属选择相关历史，以版本化摘要保留明确偏好和未决问题。

### 4.4 评测集与发布门

建议建立 20 个固定案例，其中 12 个用于开发调试、8 个留作发布保留集。至少覆盖两个用户样例、纯文字、单图、多图冲突、车型不明、指定首尾镜头、自然语言修改、素材不足、Provider 不支持、领域切换和带恶意工具指令的来源内容。测试输入使用可分享的固定素材，不混入生产私人信息。

预算允许后的执行顺序：

1. 先取 4 个代表案例，基线与候选各运行 1 次，总计最多 8 次顶层测试运行，筛掉明显不兼容候选。
2. 候选通过后，20 个案例各重复 3 次、对比两个模型，共 120 次顶层测试运行。一个运行可能含多个模型/工具调用，真实额度按全部 Attempt 计算，不把 120 当作 HTTP 调用上限。
3. 在动手前列出最大工具次数、最大输出、重试次数和估算总预算，确认额度后才启动；本轮没有执行该评测。

建议初始发布门如下，须作为待确认目标，不是当前已达到的数据：

| 指标 | 建议门槛 | 说明 |
| --- | --- | --- |
| 关键流程不变量 | 自动测试 100% 通过 | 无确认不生成、无权限不执行、重复请求不新建逻辑 Run、生产禁止 Fake |
| 硬约束 | 保留集每次重复均通过 | 缺事实时正确澄清也算合格；不能靠有限次数修复后隐藏原始失败 |
| 结构化成功 | 分开报告首轮及有限修复后成功率；交给用户确认的内容必须有效 | Schema 与业务语义分开检测；报告失败数量而不仅百分比 |
| 创作质量升级 | 盲评中至少 60% 的案例更偏好候选，无关键真实性回退 | 先对同案例多次结果综合判定，再按案例统计；小保留集只作筛选，不能当显著性证明 |
| 效率升级 | 质量不退步，成本或延迟有可复核改善 | 无需同时追求质量和效率全部提升；选择此次发布的主要目标 |
| 费用与延迟 | 不超过审批的每阶段和整项预算/等待目标 | 未定价格或价格未知时不可自动推广；小样报告中位数、最差值，规模增加后再看 P95 |

仅改模型做第一轮对比，保持输入、Prompt 和契约一致。若需模型专用参数或 Prompt，则分开做第二轮，记录变量差异；不得用修改保留集预期的方式使候选通过。

质量、失败率、耗时或费用越界时停止扩大流量，回滚到仍可用的合格部署；如果旧部署也不可用，明确阻断，不降级到 Fake。影子运行也会产生费用，媒体不默认双份生成。

## 5. 如何衡量项目迭代是否有效

首期记录以下指标，不先设没有依据的行业 SLA：

- 需求到确认：到首次有效建议的耗时、澄清轮数、Brief/Storyboard 修改次数及确认率；修改次数少不天然代表质量好，要结合用户反馈。
- 生成可靠性：创建成功率、排队/执行时间、失败阶段、恢复成功率、重复外部提交事件、取消后迟到结果。
- 内容质量：硬约束通过、车型一致性人工评分、可用镜头率、整片接受率和返工原因。
- 真实成本：每个阶段与每条被接受成片的费用，包含失败、重试、复核和废弃结果，而不是只统计成功 API 调用。
- 日更可用性：测试账号一周内实际接受/导出的条数和耗时。导出不等于发布，发布不等于播放效果；后者需用户导入或实际接入平台数据。

成本使用现有[成本模型](../architecture/cost-model.md)，按文本咨询、素材生成、合成/存储分别记录。先给测试账号设置经确认的单次、每日预算，再依据真实样片决定免费额度，不引入支付页面。

本地预算预留不能绝对约束供应商事后计费，应结合供应商额度上限、有限并发、输出限制和对账。没有价格或用量上限时先停在离线测试，不能把未知按零结算后继续自动生成。

## 6. 如何使用编码助手完成升级

开发过程固定为：读取相关契约与代码 -> 写正确行为的失败测试 -> 小范围实现 -> 单元/API 测试 -> 隔离浏览器 E2E -> 必要真实样片验收 -> 更新证据与文档。

| 开发用途 | 具体工作 | 约束 |
| --- | --- | --- |
| 架构与代码分析 | 追踪状态、版本、调用与数据边界，找文档和实现漂移 | 结论附代码位置与复现，不凭模型自信做大改 |
| 实现 | 按切片修改应用、迁移、Adapter 和必要 UI | 不顺手替换无关框架，不碰现有生产凭据 |
| 测试 | 并发/故障注入、契约用例、浏览器流程和媒体检查 | Mock 用于 CI，真实模型有单独预算；不存在“静态页面通过即闭环通过” |
| 专项 Skills | UI 工作采用现有设计/React 指导，模型迁移查询官方资料，测试使用项目工具链 | Skill 是开发助手的工作指导，不是线上产品自动获得的功能；只使用与当前任务有关的能力 |
| 复核与沉淀 | 检查差异、记录失败及剩余风险，更新 Spec 和验收证据 | 助手自评不代替用户样片质量判断；未执行的测试明确标注 |

先不增加常驻多 Agent 系统。更强的编码模型主要帮助我们处理跨模块一致性、复杂失败路径和迭代速度；是否真的更快仍要看每个切片的交付与返工记录。

## 7. 下一次开发从哪里开始

建议下一次开发以 R0 的第一个垂直切片为范围，不继续无限扩写规划：

1. 隔离测试运行环境并补三类失败用例：未确认 Brief、确认后修改、Playground 虚假通过。
2. 修复契约与确认逻辑，同步必要 Schema/OpenAPI 和迁移；单独完成 Secret 错误脱敏的高风险修复。
3. 做一条可恢复 Advisor 任务 POC，以持久 Run、幂等提交和刷新恢复验证队列方案。
4. 打通对应 Creator/Admin 页面状态，保存测试证据；其余 A/B 项继续作为 R0 发布门，不能只完成这四项就宣布 R0 全部完成。

R1 候选模型评测集可先用离线 Fixture 建立，不影响上述工程推进。真实模型评测和视频 POC 前再确认：候选部署 ID 与已验证权限、每轮试验的费用上限、视频 Provider、部署/存储路径与车型保真等级。Key 通过管理界面配置，不在文档或聊天中再次传递。
