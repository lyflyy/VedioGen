# 策略与分镜流程修复、真实成片验证

日期：2026-09-08。范围：企业内部 MVP，不引入付费视频供应商或正式版本审批。

## 本轮问题

用户反馈真实项目 `323873ba-8568-474e-b956-ada42cc7263c` 的策略方案堆叠、模型等待无反馈、上传不绑定、保存不明显、缺素材也跳过分镜，以及无法从文字走到最终视频。

保留用户已编辑的分镜和 17 份素材，不把复杂项目改成简单图片片。另建纯文字项目验证真实链路。

## UI / UX 设计依据

使用本机 `frontend-design`、`web-design-guidelines` 与 React 最佳实践技能，结合已有企业内部工作台设计。核对 Web Interface Guidelines，沿用现有 Next Image、Lucide、Button、Tooltip、Status 和响应式外壳，没有另建一套 UI 框架。

设计主次是“比较方案 > 补充反馈 > 核对事实”，不是等宽三个业务栏目。

- 颜色：白色内容面、`#f5f6f7` 工作区、现有绿色主操作、炭黑媒体舞台、`#faf1d7` 和 `#6d4a03` 警示。避免额外渐变与装饰。
- 字体：沿用 IBM Plex Sans / Noto Sans SC / 系统后备；标题收紧为工作台层级，长诊断使用正文，不作为大标题。
- 桌面：主内容占剩余宽度，右侧 260px 对话；三种方案同排、按钮底对齐，事实与约束独立置于下方。
- 平板：方案在前，对话移到下方。手机：主内容在前，方案区域横向滑动，保留部分下一项以提示还有方案，页面本身不横向溢出。
- 分镜：左侧时间线，中间素材与真实试片，右侧参数与素材缩略图；高度由内容决定，移除固定短网格行导致的互相覆盖。移动端命令区进入正常文档流。
- 原始对话可展开，当前反馈框始终可用；保存、上传绑定、缺口、等待、失败都明确呈现。

```text
Desktop
| 时间线/导航 | 创意判断 + 横向叙事方向比较 | 补充对话 |
|             事实、约束与项目素材                    |

Mobile
| 创意判断                         |
| [方案 A] [方案 B ... ->]          |
| 补充对话                         |
| 事实与素材                       |
```

真实项目截图尺寸 1440、1024、390，均无页面横向溢出；1440px 下三个方案宽度均 292px、顶边一致。手机对话起点位于主内容之后。截图见 `.data/internal-mvp/strategy-after-{width}.png`。

## 修复与能力

1. 脚本生成改成持久后台任务。点击确认后立即出现准备素材、生成脚本、匹配素材、检查执行条件等实际阶段与等待秒数。刷新恢复任务，失败可重试。
2. 不展示或伪造模型内部思维链，也不编造百分比。当前网关是结构化请求，阶段信息来自服务器实际执行，不是 token 流或模型推理过程。
3. 上传接口返回素材对象，前端立即把它绑定至点击上传时的镜头；图片、视频、GLB 使用相应来源，缩略图和预览立即反映选中项。
4. 保存分镜更新已保存状态并提示成功，不跳转。确认分镜先保存，再执行逐镜头条件检查；缺素材时留在当前页说明原因。
5. 无项目图片时，后台调用 GPT 提取主体，复用品牌官网适配、受约束的下载器和 ffprobe，从同一图库组准备最多三张图片。随后生成脚本并匹配未绑定的图片镜头。已有素材优先复用。
6. 分镜页提供“自动准备素材”，不覆盖已有绑定，不把 Blender 或用户视频镜头改成图片动画。联网与模型请求不占用生成锁；写回时检查分镜变更及正在运行的视频任务。
7. GPT 素材匹配接入已有多模态图片输入，最多前四张附图，其余仅有元数据；匹配只接受真实素材和镜头 ID。不能把参考图等同于动作已完成。
8. 修复中英文双品牌名称：`张雪机车 ZXMOTO 820RR` 可定位已支持的官网车型，仍不把未知车型替换为 820RR。
9. 修复透明 PNG：编码前按媒体底色进行 alpha 合成，避免透明区域的隐藏 RGB 在 YUV 视频中形成杂色和边框。新增真实解码像素回归。

## 接口与部署约束

- `POST /projects/{id}/storyboard-runs?background=true`：202 返回任务；项目当前 Brief 必须已确认，相同项目的活动请求复用。默认 false 保留旧同步模式。
- `GET /projects/{id}/storyboard-runs/latest`：返回 `{run: ...}`，包含状态、阶段、事件时间、警告、错误和完成的 storyboardVersionId。
- `POST /projects/{id}/storyboards/{sid}/auto-materials`：同步准备与匹配，返回分镜与 materialWarnings。并发编辑返回 409，不覆盖用户修改。
- `GET /projects/{id}/storyboards/{sid}/readiness`：真实执行计划的逐镜头检查，不是画质或内容一致性验收。
- 使用现有 DocumentRow 存储任务，不新增消息队列服务。单 API 进程、单脚本工作线程；不支持多副本协调。
- 服务重启后，未完成脚本任务标记 interrupted，需手动重试，不自动重复调用付费 GPT。当前未实现供应商查询恢复或脚本取消。
- 图片下载可能部分成功；失败会保留已入库素材和明确状态。未知品牌、具体配色及特殊场景不保证自动匹配，未确认信息保留警告。
- 8001 API 已重启到新代码，3001 保持可用；没有改动 3000/8000 或本地 ComfyUI。

## 真实视频证据

项目：`61854956-1af0-4704-8114-16510f40416b`。

输入：张雪 820RR，配色不限，12 秒、3 个镜头、仅图片运动、短字幕、无旁白/音乐。不要求三维环绕或骑手。全程无用户上传。

实际过程：浏览器创建项目 -> GPT 创意建议 -> 采用方向 -> 确认 Brief -> 后台 GPT 脚本 -> 官网图片准备 -> GPT 图片匹配 -> 保存 -> 单镜头试片 -> 确认分镜 -> 本地 FFmpeg 合成 -> 页面播放与下载。

首次实测因双品牌名未归一化导致官网素材没有准备成功；修复后通过页面“自动准备素材”继续已有脚本。首次画面发现 PNG 透明合成问题及元数据匹配角度错误，加入 alpha 合成与真实图片输入后重新匹配、试片及生成。测试项目的旧成片保留，不冒充首次一次成功。

- 官网图片：同一配色组三张白色 820RR，来源 `https://www.zxmoto.com/index.php?c=show&id=58`。
- GPT 实际调用审计共 6 次成功：创意建议 1、主体提取 2、脚本 1、素材匹配 2，含上述修复后的重试。未调用 fake，也未调用付费图片或视频 API。
- 脚本调用约 21.1 秒；最终视觉素材匹配约 11.8 秒。费用仍以中转站账单为准，不能宣称免费。
- 输出：1080 x 1920，30 fps，H.264 + AAC，12.010667 秒，924327 字节。音轨为静音，无虚构引擎声。
- 最终 Artifact：`a6b72b72-ff69-47d8-a1e0-a51b3bd6acb0`。
- 文件：`.data/internal-mvp/text-workflow/zxmoto-820rr-simple.mp4`。
- SHA256：`0023241104cced46384f52c2be3ab07edab6cbdc07f9c042177edad7a87efca9`。
- 浏览器播放时间推进至 0.66 秒；抽样帧 0.2 秒与 2.5 秒有 785 个显著变化的 RGB 通道；桌面与手机播放页面无横向溢出，页面运行错误为零。
- 证据：同目录 `result.json`、脚本等待截图、分镜/试片/成片桌面与手机截图。运行器 `scripts/local-video/verify-text-workflow.mjs`，默认可恢复，须显式 `RUN_TEXT_WORKFLOW=1` 才会执行真实调用。

## 尚未完成

这是一支基本图片展示短片，不是“80 分影视级”验收。尚有大面积竖屏留白、简单运镜、无节奏音乐等质量差距。不能宣称已实现任意纯文字生成真实车型的任意场景。

原项目保留 6 镜头：前 5 镜头为 image-to-video 且尚未绑定；最后驾驶镜头为 user-video，项目中没有骑行视频。用户可通过修复后的自动准备/选择图片进行单镜头尝试，但图片不会补出真实骑行片段，图生视频也不能保证精确完整 360°。本轮没有静默更改这些来源或内容。

下一步是精确车型几何与驾驶镜头的专项能力验证，以及自动素材构图、同车同色和镜头表现的质量评测。应继续由平台准备，不把用户必须上传作为唯一方案。
