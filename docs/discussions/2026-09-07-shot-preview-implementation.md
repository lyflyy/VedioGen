# 单镜头试片、真实流程与发现的缺陷

- 日期：2026-09-07。
- 本轮完成单镜头试片能力与真实工程流程；正式车型选择、完整难镜头和 80 分验收仍未完成。
- 用户只有文字，参考素材继续由平台准备；没有调用付费图片或视频接口。GPT 调用使用既有配置，仍可能产生文本 API 费用。

## 发现与实现

原执行计划在任一镜头缺少能力或素材时拒绝整个任务，无法先验证已准备好的镜头。本轮新增 [单镜头试片规格](../specs/shot-preview.md)所述能力：草稿保存、仅当前镜头入队、播放、下载、停止、恢复、按原参数重做、采用到当前镜头。沿用原任务表和单媒体队列。

试片不生成最终成片、不更新项目完成状态，也不覆盖已有整片运行指针。采用只复用实际视频文件并改变对应镜头来源；其他镜头、顺序和完整时长保持不变。页面区分本地模型、云端模型、图片运动与视频素材。

真实流程还发现并修复两个此前隔离测试没有暴露的问题：

1. **代理超时**：真实 GPT 创意建议用时 36.849 秒，后端成功保存，但 Next.js 代理默认在 30 秒断开，开发日志记录 socket hang up。读取安装版本的 `proxy-request.js` 和 `config-shared.d.ts` 后，将 `experimental.proxyTimeout` 设为 650000 毫秒。修复后实际分镜请求经 3001 网页代理用时 36.26 秒、HTTP 202，未在 30 秒断开。没有因此重复调用已保存的创意建议。
2. **分镜映射丢字段**：模型 wire schema 已有 subject/action/scene，但 `_runtime_storyboard` 丢弃了这三个字段，页面与 videoPrompt 仅使用概括 description。这会把具体场景和动作弱化成情绪描述。本轮保留结构化字段，并把它们及 mustShow/mustAvoid 放入视频提示词，新增回归测试。同时强化所有用户指定中段为硬约束、完整 360 度不能改成“环绕感”的提示约束。提示约束不等于生成模型必然遵守，仍需预览检查。

旧分镜不做静默回填；在相同工程项目中通过正常 storyboard-runs 端点重新生成。旧文档保留，没有直接修改数据库伪造 GPT 输出。

## 失败和恢复记录

- 第一次页面导航等待整体 load 超时，没有创建项目或调用模型。改用 DOM 就绪及具体控件检查。
- 第二次已创建项目，但 waitForURL 仍等待整体 load；创意建议在后端成功，前端还遭遇前述代理超时。后续通过同一项目 ID 恢复，不重新生成建议。
- 首份分镜检查未发现具体沙漠要求，追查到映射丢字段；修复并显式重新生成分镜，而不是放宽验证以宣称通过。
- 官网第一次检索终态为 failed，提示访问超时。确认页面恢复 HTTP 200 后手动重试，使用原项目与分镜；不是因观察超时就重复提交。
- 本地模型只提交一次。查询、页面刷新、采用和下载没有重新发起 GPU 生成。

`scripts/local-video/verify-shot-preview.mjs` 是显式启用的真实脚本，不被隔离 E2E 调用。`RUN_REAL_SHOT_PREVIEW=1` 才可调用既有 GPT 与本地模型；`SHOT_PREVIEW_PROJECT` 用于继续已有工程项目，查询已有分镜/试片，不盲目创建新任务。官网终态失败后仅显式 `RETRY_REFERENCE_SEARCH=1` 才重试检索。

## 画质结论

**不通过正式使用。** 抽帧可见：后段生成了原图没有的手部；小字和仪表细节不能保持完整；横向参考 contain 到竖屏后有大块灰色填充。中间 0 和 N 大体保留，不代表整块仪表或真实车辆状态准确。

工程中的“采用”只验证文件复用及单镜头绑定，不是人工画质通过。没有把该片标记为真实转速变化、正式成片或 80 分验收结果。

下一步应先改善仪表镜头的竖屏构图和可控细节保真，重新评估此类镜头是否需要扩散模型；用户没有要求转速数字变化，不能自行编造车辆状态。其他四个难镜头继续准备匹配资产，不能用仪表片或湖边骑行替代。张雪 800X 的可靠参考与三维几何也仍有缺口。
