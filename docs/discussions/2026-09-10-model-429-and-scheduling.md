## 根因与不确定性

1. 429 和 5xx 都被归为 PROVIDER_UNAVAILABLE，丢失限流语义，不解析 Retry-After。
2. 没有凭据级暂停机制，创意咨询、素材规划、脚本与匹配可继续使用同一受限凭据。
3. 路由配置包含 maxAttempts、fallbackOn，但执行器原先直接遍历所有备用部署，没有落实这两个配置。此缺陷本次一并修复，但不是上述七条日志中已证明的直接原因。
4. 管理页顶部“可用”标记是静态文字，部署 ready 也只是配置状态，并不证明当前服务健康。已移除静态“可用”，并为凭据和部署显示实际暂停状态。
5. 原失败调用耗时记为 0；现在真实请求开始时记录 calling，失败记录实际耗时。重启将未结束的 calling 标记为失败，不自动重发。

历史记录只保存“模型平台返回 HTTP 429”，没有保存上游错误子码或 Retry-After，无法追溯究竟是频率、并发、余额、额度还是中转站的上游限制。未调用真实接口，因此没有证明中转站目前已经恢复。

参考已实际读取的 [OpenAI 错误文档](https://developers.openai.com/api/docs/guides/error-codes)：429 可表示请求速率限制，也可表示余额、组织或项目额度限制，应尊重 Retry-After。该说明用于协议分类设计，不意味着第三方中转站必然采用相同语义。

## 新执行规则

- 一次 429 立即结束当前模型请求链，不自动重试、不切换备用部署，即使 fallbackOn 包含 RATE_LIMITED。
- RATE_LIMITED 使用 Retry-After 秒数或 HTTP 日期；未提供或无效时默认 60 秒。冷却到期仅允许后续请求，不自动重新生成。
- 明确的 insufficient_quota、credit_balance_exhausted 及已知额度限制代码归为 QUOTA_EXCEEDED，暂停凭据直到管理员处理后明确恢复或更新凭据。
- 新增 model_cooldowns 表，按凭据 ID 共享并持久化。刷新页面、换项目或切换能力不会绕过冷却；服务重启保留暂停。
- 冷却中直接返回“未发送请求”，不新增上游模型调用记录。已在 429 到达前发出的其他请求不能被追溯取消；本轮没有实现多副本全局速率控制。
- 创意建议和同步脚本返回 HTTP 429，临时限流附带 Retry-After；后台脚本进入 failed，记录 errorCode/retryAfterSeconds，不继续调度素材匹配。
- 模型配置探测也检查共享冷却；不能通过“能力探测”或“连通性测试”绕过暂停。
- `/admin/model-credentials` 和 `/admin/model-deployments` 返回可空 cooldown，包含 errorCode/message/retryAfterSeconds。界面显示需要处理与具体说明，探测失败后刷新该状态。
- `/admin/model-credentials/{id}/cooldown-reset` 只允许手动解除额度暂停或已结束的冷却；未结束的限流仍返回 429。凭据页“恢复调度”先确认用户已处理额度；恢复动作不发出模型请求，不保证供应商已经恢复。
- 凭据轮换清除旧凭据的暂停信息。新建另一个凭据配置或其他供应商不共享本凭据 ID 的冷却，仍需后续账户级配额治理。
- 其他错误仅在 fallbackOn 明确允许时使用备用部署，总尝试数受 maxAttempts 限制，重复部署 ID 去重。
- 不打印供应商错误原文或密钥。只读取已知错误子码，输出受控说明。未修订历史失败记录，避免伪造当时不可获取的信息。
