# 生成成本核算模型

- 状态：草案
- 建立日期：2026-09-05
- 目的：在没有历史运行数据时，用可测量数据决定免费额度、质量档位和资源预算

## 基本原则

首期虽然不收费，但每次生成都必须计算内部成本。免费只代表用户支付为零，不代表系统可以无限使用 GPU 和外部 API。成本控制应通过审批门、预览档、每日额度、缓存和逐镜头重试完成。

不在没有基准数据时承诺具体的单条成本。先完成 P0 垂直切片并记录真实数据，再制定目标。

## 单条视频成本

```text
C_video = C_llm
        + C_image_video_generation
        + C_tts_music
        + C_blender_gpu
        + C_composition_cpu
        + C_storage_egress
        + C_retry
        + C_fixed_allocation
```

- `C_llm`：创意、脚本、分镜、改写、事实核查所用 Token。
- `C_image_video_generation`：生图、生视频、抠图、超分和帧插值 API 或 GPU 时间。
- `C_tts_music`：配音、语音识别和音乐生成。
- `C_blender_gpu`：每个镜头的 GPU 小时乘以实际算力单价。
- `C_composition_cpu`：编码、字幕、音频混合和质检消耗。
- `C_storage_egress`：上传、代理文件、中间帧、成片保存和下载流量。
- `C_retry`：模型失败、渲染失败和用户允许的重新生成。
- `C_fixed_allocation`：数据库、队列、监控和空闲 Worker 等固定成本按有效成片分摊。

## 必须记录的账本字段

每个 GenerationRun 和 Shot 至少记录：供应商、模型/Worker 类型、计价单位、输入数量、输出数量、开始/结束时间、GPU/CPU 秒数、峰值显存、缓存命中、重试原因、产物字节、成功状态和归一化人民币成本。

估算值和结算值分开保存。提交最终渲染前显示预计资源消耗，运行后写入实际消耗，便于发现估算偏差。

## P0 基准方案

使用同一真实摩托车资产和同一 15 秒 Storyboard，包含三个 5 秒镜头：整车英雄镜头、运动跟拍、机械细节特写。分别测量：

1. Eevee 或低采样 Cycles 的 540 x 960 预览。
2. 1080 x 1920、30fps 的最终 Cycles 档。
3. 一次单镜头失败后重试，不重复其他镜头。
4. 一次脚本修改但画面不变，验证复用已渲染镜头。
5. 完整配音、字幕、音乐、FFmpeg 合成和自动质检。

至少重复三次，记录中位数和最差值。P0 结果应回答：每帧/每镜头耗时、峰值显存、单条实际成本、主要成本来源、缓存节省比例和失败放大系数。

## 免费阶段资源控制

- 脚本和 Storyboard 确认前不启动最终渲染。
- 预览使用低分辨率、低采样和代理资产。
- 以镜头为缓存和重试单位；文案修改不应强制重渲未变化画面。
- 每个用户设置每日项目数、最终渲染次数和重新生成次数。
- 队列按预览和最终渲染分级，防止单个用户占满 Worker。
- 车型、场景和镜头模板预热并复用，能预渲染的固定镜头优先复用。
- 外部模型调用设置硬预算和超时，失败后使用已确认的降级策略。

## 成本决策门

完成 P0 后再确认以下数值：

- 单条 15 秒和 30 秒视频的预览成本与最终成本。
- 免费测试用户数、每人每日条数和全站每日预算上限。
- 可接受的平均排队时间、P95 完成时间和失败率。
- 预览、标准、高清三个质量档是否都有存在价值。
- 自有 GPU、云 GPU 和外部视频 API 的临界使用量。

在这些数值确认前，架构保留计量、限额和多档渲染能力，但不设计付费、套餐或充值页面。
